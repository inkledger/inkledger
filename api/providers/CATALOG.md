# Provider catalogue

Every service the provider layer is meant to talk to, mapped onto the contract (v1, frozen): `contracts/providers.ts` for capabilities and traits, `api/providers/types.ts` for the operations. The contract was checked against all of them, not only the built ones, and every entry of `catalog.ts` parses in the contract's own schemas.

Where each thing lives:
- `catalog.ts` is the structured source.
- The matrix below is a view generated from it.
- This document explains the semantics.
- `docs/dev/spikes.md` holds the assumptions still to verify.

The contract changes only when a real adapter shows that a service can't be represented without lying about it or faking a capability, or when a contract test shows an invariant v1 can't express.

Two kinds of statement appear here, and they are kept apart:
- **Service facts**: endpoints, limits, payloads, formats. They come from each service's API documentation as of October 2026.
- **inkledger mapping**: the layer's policy. This covers `local` time, recreating instead of updating, the conservative value of anything unverified, and reconciliation.

A value still to verify on a real account is marked `(verify: <id>)` in `catalog.ts`. The `<id>` is a row of the spikes table, which says what the spike checks and what changes if it holds. Until then the catalogue keeps the conservative value. A test checks that every marked id has its row.

## How to read it

- **Capabilities** are what the layer can do with a service. Each one is an operation; `core/validate.ts` checks both directions (no capability without its operation, no operation without its capability).
- **Traits** say what the service has that the layer doesn't operate yet: creating issues, relations, attachments, timeboxes, fields. They enable nothing.
- **Adapter status** is the build state of inkledger's adapter (`registry.ts`): planned, experimental, built, disabled. It is not an issue status.
- **Time sinks** (Tempo, Harvest, Clockify, Toggl, Everhour) handle no issues and no workflow, only time. Each exposes a subset of the time operations (Everhour has day totals; Clockify has no feed; a connection may be read-only); the matrix says which. Each is attached to a tracker connection, and some fit only certain trackers: Tempo references issues by Jira issue id, so it attaches only to a Jira connection. The sink checks that fit when it is attached, in addition to the reference strategy it picks.

Bitbucket Issues was removed by Atlassian on 2026-08-20 (its API answers 410), so it is not a provider.

Legend:
- **Time**:
  - `session` entries have a start; `date` entries only a day; `day totals` is one total per day and issue.
  - `update`:
    - `native`: changed in place;
    - `replace`: the whole entry is sent again, its identity kept;
    - `recreate`: deleted and logged again, its identity changing (the engine keeps the link);
    - `none`: not changeable.
  - `feed`: how changed entries are followed. See [Following and reconciling](#following-and-reconciling).
  - `local`: inkledger keeps the entries and the service has none. `local (service totals)`: inkledger keeps the entries, and a total the service shows is read only for display.
  - `counter`: the service keeps one running total per issue. inkledger keeps the entries and moves that total by each change, at a known revision.
- **Gone reported**: the departure reasons the service itself reports. `none reported` means the service reports no authoritative departure reason. Reconciliation may observe an item as absent and mark it `missing`, which is uncertainty: never treated as deleted or out of scope.
- **Webhooks**: accelerators only, with the payload mode shown always: `full` (the payload holds all the adapter needs to build the normalized object) or `signal` (it only says that something changed, and the adapter reads it back). Every event is a `signal` until its payload is verified (see the spikes).

## How each part of the contract maps

### Identity: `normalizeKey`, `parseRef`, `findIssue`, `remoteId`

**`remoteId` is the authoritative identity.** It names the object for as long as the service keeps that object's identity. When a service replaces an object instead (a GitLab move creates a new issue with a new id), the old one is reported gone as `transferred`, with its successor.

**Operations take an `IssueRef`.** It holds the `remoteId`, the current key and a container hint. The key and the container are operational, not authoritative: adapters use them to build a URL or narrow a call, never to decide which object it is.

Keys move:
- Jira: project move;
- GitHub: transfer;
- GitLab: move;
- Linear: team change;
- YouTrack: project change.

When an old key comes back, the engine keeps it as an alias.

**`parseRef`** classifies what someone pastes (key, URL, permalink) without I/O. **`findIssue`** resolves it to one of:
- found;
- none;
- ambiguous: at least two distinct issues, never a silent pick.

### Probe: what a connection really has

`probe` reads, for one connection:
- plan;
- permissions;
- the service's configuration (time tracking on or off);
- the active workflow sources;
- the rate limit the connection meets.

It returns effective capabilities, which may only **narrow** the static ones: fewer operations, tighter limits. They never widen them. `core/validate.ts` refuses a probe that claims more (`incompatible`), and the active workflow sources must be distinct and of declared kinds.

The rate limit comes with its origin:
- `detected`: from the service's headers;
- `configured`: by the user;
- `typical`: the published figure.

A sink's `typicalRateLimit` in the matrix is indicative only. Throttling uses the connection's effective figure and the service's own rate-limit errors (`rateLimit`, `retryAfterMs`).

### `listChanged`: passes, pages, checkpoints

**Passes.** A pass is read page after page; the checkpoint comes with the last page and is stored only then.

**Binding and invalid checkpoints.** Checkpoints and page tokens are bound to provider, connection, stream, format, and (for tokens) the pass. Anything else is `invalidCheckpoint`, and the engine reads everything again. A page token that comes back within a pass is refused, so a loop can't run forever.

**"Mine".** It is configurable per connection: assigned, involved, watched, or pinned containers. The defaults:

**Departures.** A service reports only the departure reasons in its `sync.gone` (`ReportedIssueGone`). Everything else, and every disappearance with an unknown cause, is the engine's `missing`, found by reconciliation. `missing` is never treated as deleted.

A webhook such as Jira's `issueRemoved` is a signal to look again, not a reported reason.

### Workflow: sources, `statuses`, `transitions.list` / `apply`

Statuses stay the service's own. Categories only group them: either native, or by a versioned mapping of the connection.

Sources:
- **workflow** (jira): transitions with required fields (`expand=transitions.fields`). On Server, `hasScreen` is absent, so only `fields[*].required` counts.
- **allowedList**:
  - azure: states of the work item type, plus the process rules;
  - youtrack: `possibleEvents` (send the event, not a value);
  - openproject: the form's `status.allowedValues`, with `lockVersion`;
  - redmine: `include=allowed_statuses`.
- **direct**: the destination is assigned directly, with no transition object in between. This is about how a status is set, not a promise that every status is allowed: the service may still refuse one for this connection or item (`forbidden`, `invalid`). Used by linear, shortcut, plane, clickup, wrike, monday, notion, the GitHub project status, and labels.
- **move**: the item moves to a column (trello, basecamp, asana sections, gitea boards, todoist sections, planner buckets).

**Who carries out a transition.** The core decides from the transition's fields whether inkledger can carry it out. With a required field of a type inkledger doesn't know, inkledger doesn't carry it out: it points to the service's own page when there is one (`remoteUrl`), and otherwise it says that the transition has to be done on the service.

### Time

**Models.** A tracker's time is one of:
- `entries`: the service keeps the entries;
- `counter`: the service keeps one total per issue;
- `local`: the service keeps nothing.

A sink always has entries, in one of two forms:
- **Entries.** Each entry stands alone, with a start (`session`) or only a day (`date`).
- **Day totals** (Everhour). There is one total per user, day and issue, not individual entries. `setDayTotal` replaces the day's total with the sum of inkledger's own entries for that day; a total of 0 removes the day.

#### Following and reconciling

These are two separate things, and the matrix shows both.

**Feed** (`changed`): how changes are followed between passes.
- `incremental`: resumes from an adapter-owned, persistable checkpoint: a native service cursor, or a monotonic watermark on a change filter the service applies. The adapter may overlap boundary values to lose nothing, and ingestion removes the duplicates; that overlap doesn't make it a window. `with removals` means the service also reports deleted entries, so `changed` can return `ReportedEntryGone`.
- `window by entry date` / `window by change`: no persistable checkpoint; each pass reads again a range relative to now ("now minus N days").
- `none`: there is no change feed.

**Reconcile** (`reconcile.kind: period`): every entry of a period can be read and compared with inkledger's own, in spans of at most `maxDays`. This is how deletions without a feed, and anything a feed missed, are found.

A service with `feed none` can still sync when it supports period reconciliation (all catalogued ones do).

#### Protected writes

- **Idempotency key.** Every create carries one.
  - `native`: the service honours it, so a retried write lands once and can be retried automatically.
  - `local`: only inkledger's own de-duplication applies, with one write at a time per entry; a retry after an unknown outcome reads back first.
- **Revisions.** With `concurrency: revision`, every change sends the revision it was based on (`expectedVersion`, required). If someone else changed the entry, the service answers `conflict`.
- **Delete** is idempotent: an entry already gone counts as deleted.
- **Locks and approvals.** The capabilities say what the service supports in general (`approvals.read`, limits such as `maxAgeDays`). Each entry says what can be done to it now: `editable`, which is never true while it is `locked`, with the lock's cause. The entry is authoritative for operations.

#### Engine policy: authority

- When a Tempo connection is active for a Jira connection, Tempo is the authoritative source and destination of that connection's worklogs: Jira's own worklog import is off, to avoid counting time twice. Jira worklog ids mirrored by Tempo are kept as aliases for de-duplication.
- `local` and `counter`: inkledger is the register of the entries; a service total is never the source of an entry.
- `recreate`: the engine deletes and logs again, and keeps the link from the old remote id to the new one.

#### Time sinks: references and targets

**References.** A sink entry has to point back to its issue. The strategies, listed in order of preference (the order is behaviour; `pickReference` takes the first one that fits):
- `external`: an external reference field (Harvest `external_reference`);
- `issueId`: the tracker's issue id itself (Tempo);
- `projectTask`: the project/task the entry is filed under;
- `description`: the key in the description, as the last resort.

**Targets.** A target is the project/task an entry is filed under.
- `none`: the sink has no such thing.
- `optional` / `required`: it may, or must, have one. Targets are found either by `search` (inkledger lists the sink's projects and tasks) or by `manual` entry (the user types the id).

### Comments

**Reading and writing.** Comments are read in the service's format (each comment says its own) and written as CommonMark. The adapter keeps exactly what `writePreserves` lists and warns about the rest. Warnings reach the app without their server detail (`publicConversionWarning`).

`idempotency` works as for time.

| Format | Providers |
| --- | --- |
| ADF (Cloud) / wiki markup (Server) | jira |
| GFM / GLFM | github, gitea / gitlab |
| CommonMark | linear, youtrack, shortcut, openproject, todoist, trello |
| HTML | azure, plane, asana, monday, wrike, basecamp |
| textile (or markdown, per instance) | redmine |
| rich text (structured) | clickup, notion |

## What the contract does not carry, by design

- **Workflow editing** (creating statuses, changing schemes): the service's job.
- **Custom field writes beyond a transition's required fields.** They are read-only, under "Other fields".
- **Boards and views as objects.** inkledger's boards are its own (buckets); a service's column order comes with its statuses.
- **Webhooks as a source of truth.** They are accelerators only, and reconciliation never depends on them.
